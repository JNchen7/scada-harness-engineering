# 问题推演：网关操作结果未知时如何恢复

[问题索引](index.md) · [完整设计](../../design-docs/15-Web网关配置版本与自动回退设计.md)

假设升级命令已经发出但回复丢失，怎样判断下一步？下面讨论服务状态、持久化意图和数据库提交之间的关系。

## 失败场景

活动程序、配置与回退目录反复移动，多个步骤之间可能中断。命令返回失败时又无法简单确定远端是否执行，重试可能覆盖证据或恢复到错误版本。服务在启动和停止过渡态时，直接发命令也不一定得到预期状态。

## 建议设计

独立版本目录保留旧版原位，通过服务路径切换生效；动作前记录意图，动作后读回状态；程序和配置版本分别校验；最终激活由中心事务完成。自动恢复与重启后的恢复采用相同状态判断。

## 最难的分支

| 分支 | 正确判断 |
| --- | --- |
| 命令回复丢失 | 查实际服务路径与任务状态，不盲目重放 |
| 激活事务返回异常 | 先查是否已提交，再判断是否恢复 |
| 旧路径已经恢复 | 继续启动和验收，不再切到更旧版本 |
| 服务仍在过渡态 | 等稳定状态后决策，未停止不得替换 |
| 新程序只发 starting | 不算部署成功 |
| 匹配版本报告采集错误 | 不能让“版本正确”覆盖健康失败 |
| 中心中断 | 根据持久化记录接手，不能依赖原进程内存 |

## AI 协作中的关键点

让代理先列出状态和失败后的可观察事实，再修改执行器与页面。检查共用启动、停止和恢复入口，避免修复一条路径却让另一条重启路径仍能绕过屏障。

回归关注行为顺序、重复恢复、数据库结果未知和非致命清理失败。真实服务管理器和实机窗口另有验收要求，不能把纯模拟结果当成全部完成。

## 为什么适合面试讨论

它展示的是分布式操作中的不确定性处理：远程动作与数据库不共事务，成功响应不是唯一事实，恢复也必须幂等。可解释状态比“捕获异常后重试”更有工程价值。
