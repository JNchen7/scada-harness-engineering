# 问题推演：报警统计与数据库迁移

[问题索引](index.md) · [报表详细设计](../../design-docs/14-报表分析详细设计.md)

假设需要按设备汇总故障，并允许调整分类和时长规则，应该怎样处理区间归并及迁移重入？下面给出问题分析和验收思路。

## 为什么表面正确仍会出错

多个短报警先归并再应用时长阈值，会把本应排除的报警拼成合格故障。嵌套区间只比较上一行，会错误拆分故障。即使函数修对了，旧迁移重新执行也可能覆盖成旧定义。

这些问题跨越业务数学、查询实现与数据库演进。仅审查一个 SQL 表达式不足以完成用户结果。

## 建议契约

当前点表分类 → 单条完整生命周期阈值 → 窗口裁剪 → 按设备使用此前最大结束时间归并。保养排除作为后续已定义的统计处理，原始报警保持不变。

旧迁移不覆盖已存在的后续函数，新迁移拥有对应规则版本。迁移重入要验证业务行为不倒退，而不是只判断有没有报错。

## 回归证据应如何组织

| 维度 | 样例 |
| --- | --- |
| 数据 | 短报警、长区间包含短区间、后续延伸、首尾相接与真实间隔 |
| 时间 | 跨查询边界、活动报警、统一有效结束时刻 |
| 配置 | 分类和阈值修改立即影响历史解释 |
| 迁移 | 新库顺序升级、旧库升级、后续迁移后重跑旧迁移 |
| 展示 | 汇总次数、TOP 实例数、成员明细与导出口径一致 |

## AI 开发中的控制点

用手算得到预期结果的小样例约束生成的 SQL；要求代理检查迁移调用方、报表入口和导出，而不是只修一个测试。红绿回归证明原问题能够被暴露，最终报告标明这只是所测环境的结果。

## 可解释的取舍

动态实例不落表，使分类和规则可立即生效，减少需要同步的派生副本；代价是查询开销需要持续观察。没有规模证据时不提前引入复杂物化平台，也不声称动态计算适合任意数据量。
