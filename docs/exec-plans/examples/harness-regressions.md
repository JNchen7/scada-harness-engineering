# 问题推演：检查器如何避免漏检

[问题索引](index.md) · [机制说明](../../engineering/HARNESS.md)

假设已为 AI 开发建立规则检查器，还应怎样判断它能发现偏离？下面从语法、路径和范围选择三个方向设计反例。

## 问题不在业务代码一处

| 缺口 | 可能产生的错误结论 | 修正方向 |
| --- | --- | --- |
| 按一种引号写法识别验证调用 | 换一种引号后违规入口被漏过 | 用语法树核对命令与参数 |
| 只查采集源码顶层 | 子目录中的禁止协议调用漏检 | 覆盖实际生产源码目录树 |
| Git 转义中文路径 | 文档范围误选或禁跟踪目录漏判 | 显式处理原始路径，加入真实 Git 夹具 |
| 边缘页面嵌入后端源码 | 只选择后端测试，漏掉浏览器行为 | 将该变化映射到跨端范围 |
| 差异命令失败却保留部分清单 | CI 以不完整输入挑选小范围 | 丢弃不可靠清单，回退 All |

## 修改并不止于“补一条判断”

需要一起检查调用语法、允许集、子目录遍历、路径解码、CI 的三种触发路径以及 PowerShell 兼容。只在当前工作树跑一次通过，很可能继续漏掉负向场景。

## 验证怎样设计

违规样例应被拒绝，有效样例应通过；变化清单获取失败必须回退；中文文件名需要真实 Git 创建和读取过程验证，不能只给函数传一个已解码字符串。PowerShell 5.1 既做解析，也实际执行相关检查。

## 对 AI 协作的意义

代理的“遵守规则”需要工具反馈支撑，而工具本身也可能有盲区。把一次发现变成 Harness 回归，能让同类错误在后续任务中更早暴露。与此同时，静态检查仍不是安全沙箱，不能把修复漏检写成绝对防护。

## 面试可展开的问题

为什么 AST 比字符串匹配更适合这里？为什么中文路径必须用真实 Git 测试？为什么失败回退不能保留部分结果？哪些约束仍需要环境权限和人工审查？这些问题比列出“熟练使用 AI”更能展示工程判断。
