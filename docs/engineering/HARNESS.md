# Harness Engineering 架构建议

[工程索引](index.md) · [知识库](../README.md)

我建议把 Harness 设计为围绕 AI 开发的工程环境：入口提供路由，知识库提供约束，工具反馈揭示偏离，验证连接用户结果，交接让下一次任务接上当前状态。这些部分应共同工作。

## 一条规则应该如何变成机制

| 要守住的规则 | 建议实现 | 能力边界 |
| --- | --- | --- |
| 文档可发现 | 检查必需入口、分类索引、相对链接 | 链接正常不代表语义正确 |
| 当前事实只维护一处 | 明确交接入口，检查引用和稳定锚点 | 事实新旧仍需要审阅 |
| 设备只读 | 递归检查受检源码的协议调用，结合权限隔离 | 静态扫描不能代替设备层保护 |
| 常规验证不访问运行环境 | 用语法树核对字面量命令和脚本允许集 | 允许集不是通用脚本沙箱 |
| 检查失败必须被看到 | 非零退出与失败传播回归 | 退出码不能代替业务验收 |
| CI 不能漏选范围 | 路径规则、Unicode 夹具、不可靠差异回退 | 工作流和强制合并规则需分别配置 |
| 前端验收贴近使用 | 实际窗口、操作路径、异常状态与截图 | 单张截图不能证明全部交互 |

只写“禁止危险操作”无法自动发现偏离；只增加一个检查脚本也无法证明规则完整。每项检查需要明确输入、拒绝条件、失败提示和负向用例。

## 建议的任务闭环

1. 把目标、业务不变量、范围及验收条件写成任务卡。
2. 按任务读取最少必要知识；先查证，再处理真正影响结果的未决项。
3. 让 AI 比较可行方案并解释取舍；将选定契约写回正式文档。
4. 实施时检查相关调用方、状态和同类入口，避免局部修改造成不一致。
5. 按影响选择验证范围，依据失败证据修正；必要时检查实际用户路径。
6. 交付具体改变、验证与限制，更新交接及稳定知识。

## 检查器也需要被检查

建议专门构造五类反例：不同引号的命令调用、子目录中的禁止调用、Git 转义的中文路径、嵌入后端的前端页面、不完整的差异清单。测试应同时确认违规会失败、有效输入能通过、未知范围会保守回退。

这能把“希望代理遵守”变成更及时的反馈，但不能保证所有错误被发现。环境权限、业务审阅和实机验收仍有各自职责。

## 知识维护与投入顺序

先建立清晰入口、最小知识分类和一个可重复的验证入口，再根据高频失败增加检查器与回归。避免为尚不存在的规模设计复杂平台。

当前交接建议替换过时事实；稳定决定写入正式设计；完成任务退出 active，结果记录引用对应证据。应根据任务成功率、返工原因、定位时间和知识过期情况评估效果，测量方法见 [评审清单](../portfolio/方案评审与验证清单.md)。
