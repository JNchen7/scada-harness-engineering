# 工程标准与取舍

[工程索引](index.md)

## 简单且完整

建议以完整用户结果为交付单位。简单意味着减少无必要的复杂度，同时覆盖真实流程和状态；不是只修改一个文件，也不是删掉异常分支。

共享组件修改要检查实际调用方，成组控件修改要检查同组行为。对同一目标有明确依据、风险可控的关联修复可以一起完成；新业务能力和既定口径变化另行决定。

## 采用现有能力

业务工程采用显式 SQL、平台自带的序列化和日志能力、轻量 Vue 结构和原生浏览器能力。不因为“可能扩展”自动增加 ORM、消息总线、状态框架或通用协议平台。

这不是永远禁止新依赖。新增机制需说明当前消费者、可验证收益、运行代价和维护责任，并对相关路径验证。

## 审查发现分级

| 类型 | 必须提供 | 处理方式 |
| --- | --- | --- |
| 已证实缺陷 | 触发条件、证据、实际影响 | 按影响排序，修复并验证 |
| 待验证疑点 | 不确定点和验证路径 | 先取证，不写成既成事实 |
| 可选整理 | 具体维护收益和成本 | 不包装成必须修改 |

没有可核查收益时，保持现状可以是合格审查结论。重复审查先确认旧问题是否已解决，不反复提出同一建议。

## 性能约束

检查额外查询、分配、复制、锁、同步 I/O、重试和队列增长。不能靠丢弃数据、降低采集周期要求、关闭必要诊断换取表面提速。前后测量必须使用可比较输入，说明波动与未覆盖环境。

## 工程环境的一致性

若需要支持 Windows 环境，建议将 PowerShell 5.1 兼容、非 ASCII 文本编码、SDK 与依赖选择、CI 时区、Git 中文路径和本机开发进程的识别纳入工程约定。它们看似外围，却会让本机通过而 CI 失效，或者让测试误操作错误对象。

同一 checkout 保持单一写入任务，避免相互覆盖。可丢弃的开发进程和需要持久化屏障的采集服务采用不同停止规则；不能为绕过文件锁或测试失败随意强杀采集器。

## 完成与知识维护

验证与实际影响相称，已有有效证据不重复跑；新失败或范围内问题继续解决。交付后稳定契约归设计，当前状态归交接，已完成过程归成果记录。
