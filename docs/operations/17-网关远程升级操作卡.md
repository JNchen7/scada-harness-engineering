# 网关更新与恢复操作契约

[运维索引](index.md) · [版本设计](../design-docs/15-Web网关配置版本与自动回退设计.md)

建议把网关更新拆成可观察、可恢复的阶段，每一步明确前置条件和失败后的处理方式。

## 操作前

确定已授权对象、选择的程序与配置、当前实际版本和恢复目标。完整点集预检需要明确总数、启用数、停用数和变化；程序尚未准备或配置非法时，在连接远端前拒绝。

## 正常执行与屏障

| 阶段 | 可以推进的条件 | 失败时 |
| --- | --- | --- |
| 保存意图 | 任务与候选已可靠记录 | 不发起未记录的变更 |
| 准备候选 | 独立目录完整且目标明确 | 保留原活动版本 |
| 停止采集 | 协作停止并确认 Stopped | 保留等待或恢复状态，不强杀 |
| 切换服务路径 | 旧路径已知，候选可用 | 读回实际状态再决定恢复 |
| 启动与验收 | 新心跳、版本、有效采集状态匹配 | 执行既定恢复判断 |
| 激活配置 | 中心事务确认提交 | 结果未知先核对提交结果 |

## 恢复不是重复执行

实际路径已经恢复时，不再次换到更旧版本。旧版本没有恢复成功时，保留未解决任务并禁止新任务覆盖。首次部署没有旧服务，失败恢复不能写成“旧版正常运行”。

远端状态查询失败、服务过渡超时、数据库不可读都需要明确未核实项。清理失败单独记录，不能误报为主部署失败并再次触发危险动作。

## 旧路径兼容

如果系统同时存在直接替换和版本化更新两种路径，需要明确各自的状态模型，不能交叉覆盖。识别到版本化布局后，旧入口应拒绝用原方法替换。遗留任务按其原恢复契约处理后，再进入新流程。

## 完成记录

报告原始失败、恢复失败、已核实状态、当前版本与下一步，不能只给一个绿色“完成”。这类记录是 AI 可接手执行的前提，而不是事后为了汇报补写的故事。
