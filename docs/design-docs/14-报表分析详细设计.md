# 故障报表与查询算法

[设计索引](index.md) · [问题推演](../exec-plans/examples/alarm-rules-migration.md)

## 先区分报警、故障与停产

报警生命周期是事实记录；故障实例是按当前分类和规则推导的统计对象；实际生产停产还需要额外业务定义。本方案不把三者直接等同。

## 查询处理顺序

1. 按设备和地址关联当前点表分类，保留参与故障统计的报警。
2. 对每条报警的完整生命周期应用最短持续时间规则；活动报警以本次查询时刻为结束。
3. 选择与查询窗口相交的合格区间，并裁剪到有效窗口。
4. 按设备及开始时间排序，用此前所有行的最大结束时间识别区间分组。
5. 归并重叠、嵌套和首尾相接的区间，得到动态故障实例。
6. 按已定义契约扣除有效停产保养区间，再产生汇总、TOP 与明细。

阈值先于归并；否则多个短报警可能先拼成长故障。分类和规则动态生效，不回填或删除历史事实。

## 为什么不能只比较上一行

以下时间为虚构教学样例：

| 报警 | 区间 | 判断 |
| --- | --- | --- |
| A | 09:00–10:00 | 建立当前区间 |
| B | 09:10–09:20 | 被 A 包含，不能把当前最远终点缩短 |
| C | 09:30–10:10 | 与 A 连续，延伸到 10:10 |

若 C 只与上一行 B 的结束时间比较，会错误拆成第二次。正确结果为一次、70 分钟；累计每条时长则重复计算重叠。设备不同则始终分别归并。

## 指标口径

用 D 表示窗口内有效故障分钟，N 表示与窗口相交且扣减后仍有效的实例数，P 表示业务确认的固定计划分钟：故障率为 D/P，MTTR 为 D/N，项目口径下 MTBF 为 P/N。N 为零时后两者返回空值。

上面的 MTBF 是本方案用于说明业务口径的一种约定，不等同于所有场景的通用定义。实施前应由业务明确名称、日周月边界和计划分母；如果要求按有效运行时间计算，需要同步调整公式与验收样例。

## 保养排除与明细

保养登记只影响统计层。先得到原故障实例，再扣除相交保养秒数；剩余为零才取消次数，前后各有余时仍保留为原来的一次。明细展示原成员与原始时间，不能把重叠成员时长相加当作实例时长。

无纸化维保任务不自动创建这类统计排除记录，两套业务边界独立。

## 查询完整性

先归并完整候选，再按实例条件和显式上限选择结果、读取对应完整明细。提前过滤参与归并的成员会改变实例本身。候选与明细使用同一有效结束时刻，导出沿用页面已查询的口径。

## 必要样例

覆盖重叠、嵌套、相接、间隔、跨窗口、活动报警、阈值边界、分类变更、保养完全覆盖与部分覆盖，以及旧迁移重跑后的结果。查询性能可通过索引和集合处理改善，但不提前维护容易漂移的统计副本。
