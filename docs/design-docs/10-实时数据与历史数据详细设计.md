# 实时、历史与补传设计

[设计索引](index.md)

## 数据为何要分开

实时快照回答“最近一次成功读到什么”，历史回答“哪些业务变化被保存”，报警回答“一个事件什么时候开始和恢复”。把它们塞进同一张值表，会让重传、状态恢复和查询语义难以解释。

| 类型 | 边缘快照 | 历史去向 |
| --- | --- | --- |
| 普通参数与诊断值 | 最近有效值及时间 | runtime_data |
| 高频参数 | 最近有效值及时间 | runtime_100ms_data |
| 设定值 | 最近有效值及时间 | setpoint_data |
| 状态 | 最近有效状态 | equipment_status 变化点 |
| 报警 | 当前观测状态 | 原始事件入箱，再形成最终生命周期 |

## 写前保护

需要上送的结果先按扫描轮次在本地事务中保存，再进入独立上传流程。首次有效值为趋势提供起点，后续按变化和必要快照策略保存；报警只发送开始与恢复事件。

SQLite 的待上传数据按类别组织，不是简单的内存队列镜像。重启后从持久化记录继续。建议根据恢复目标选择持久性配置并采用事务性状态保护，同时评估磁盘、断电和文件系统故障的边界。

## 确认契约

| 结果 | 本地处理 |
| --- | --- |
| 完整、可解释的业务接收确认 | 一个本地事务删除本批对应记录 |
| 请求失败、超时、响应体不完整或确认不匹配 | 保留本批，后续按原身份重传 |
| 中心已接收但回复丢失 | 重传由中心幂等处理，不另造事件身份 |
| 永久无效记录 | 按已定义隔离与重放契约处理，保留原因 |

不能只用 HTTP 状态码或“请求发出去”判断业务确认。有效批次、失败退避、按表继续与恢复后积压排空都有独立行为边界。

## 质量与时间

读取失败不写零、空值或虚构业务状态。业务发生时间、接收时间、处理时间分别解释；“最老待上传业务时间”并不天然等于“排队等待时间”。边缘快照显示旧值时要同时显示其真实观测时间和错误状态。

## 趋势与导出

趋势以原始历史记录为基础分页，首查询捕获记录 ID 上界，后续页沿用。这个上界排除后来分配更大 ID 的记录，但不是数据库事务快照；并发未提交记录和历史修改仍有边界。

趋势图和导出对应当前页，历史报警导出则按同一已查询条件分批读取完整结果，两者在页面上明确区别。查询失败不覆盖旧结果的页码、条件和快照，不把旧数据伪装成本次查询成功。
