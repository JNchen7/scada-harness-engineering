# 数据量预算与容量估算

[设计索引](index.md)

建议单独维护容量模型，避免直接把采集频率乘以全部设备作为默认写入设计。以下数字是假设样例，用于解释估算方法。

## 先区分四种量

扫描量是读取次数；变化量是实际应保存的值；事件量是报警开始和恢复；上传量还受批次、重传与协议开销影响。实时快照另有内存与序列化成本，不能混入历史行数重复计算。

| 符号 | 含义 |
| --- | --- |
| N | 设备数 |
| P | 每台设备的数值点数 |
| T | 采集周期秒数 |
| r | 每次观测发生有效变化的假设比例 |
| B | 每行连同索引和存储开销的估算字节数 |
| H | 需要覆盖的离线小时数 |

理论扫描次数每秒为 N×P/T；变化写入的初步估算为该值×r，还需加首次值、快照、状态与报警事件。r 只是预算假设，最终要用实际变化分布校正。

## 一个明确标注的虚构样例

假设 10 台设备、每台 20 个数值点、每秒扫描一次、变化比例 5%，则扫描为每秒 200 点，变化记录约每秒 10 条，即每天 864,000 条。若粗估每条 160 字节，则约 138 MB/天。该值尚未计入报警、日志、备份、事务日志和额外索引，不能作为磁盘采购结论。

若全部点按 100ms 全量写入，上述同样点集将达到每天 172,800,000 条。这个对比说明为什么高频点必须单独预算，而不是声称变化上传一定节省某个固定比例。

## 断网与补传

单节点缓存预算约为每秒待上传行数×B×H×3600，再加入 SQLite 数据库、WAL、恢复空间和安全余量。中心恢复后，补传吞吐必须高于新增速度才会消除积压；同时需要限制对实时采集和中心查询的争用。

## 保护与观测

容量模型不能替代运行时保护。磁盘预留、缓存可写性、内存待落盘上限、暂停和恢复水位需要明确。无自动删除策略意味着需要容量监控和运维决策，不意味着空间无限。

优化后比较扫描耗时、滞后、积压增长、磁盘写入与中心入库吞吐；不要用单个接口微基准代替完整链路。相关契约见 [采集](09-协议适配与采集服务详细设计.md) 与 [质量](../engineering/QUALITY.md)。
