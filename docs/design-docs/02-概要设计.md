# 概要设计

[设计索引](index.md) · [架构地图](../../ARCHITECTURE.md)

## 设计目标

让现场数据在网络和服务出现故障时仍有可解释的状态，让中心业务可以独立演进，同时保持边缘采集轻量。核心设计关注可靠性与职责边界，不把功能数量作为架构复杂度的理由。

## 边缘与中心

边缘拥有设备配置、周期调度、当前值、报警变化识别和待上传持久化。中心拥有可靠接收、最终报警生命周期、历史查询、统计、账号及业务流程。两者通过明确的批量接口交换数据，不共享数据库连接。

中心采用模块化服务而非预先拆分大量微服务。数据库使用显式 SQL，值与状态采用集合入库，报警处理有唯一的生命周期处理者。Web 使用 Vue、Vite 和图表库，查询状态与业务判断分别放在适合的位置。

## 六条设计不变量

| 不变量 | 影响 |
| --- | --- |
| 读取失败不构造正常值 | 快照保留真实时间，报警不伪造恢复 |
| 接收确认前不清理待上传数据 | 超时、响应丢失和重试都需幂等 |
| 报警入箱不等于生命周期完成 | 接收延迟与处理积压分别可见 |
| 分类规则只有一个权威来源 | 历史统计动态解释，不复制多份分类 |
| 已完成采集落盘后才结束服务 | 停机依赖本地保护，不依赖中心清空积压 |
| 状态未知不能改写为成功 | 远程维护、保存重试和恢复都要核实 |

## 技术取舍

SQLite 提供本地事务与重启恢复，代价是磁盘容量、锁和写入失败需要显式处理。SQL Server 支撑唯一约束、短事务、集合入库与窗口函数，复杂统计必须具备有针对性的样例。轮询和后台处理优先复用已有服务，暂不引入外部消息队列。

## 非功能验收

验收覆盖持续采集、断网、中心异常、磁盘保护、重复上报、服务停止、查询一致性和权限。性能只在可比较环境与实际路径中判断，不因减少代码或引入缓存就宣称优化成功。

## 与 Harness 的关系

本篇的不变量需要进入领域设计和回归，而不能只放在总览里。AI 修改某一环节时，应沿相关依赖检查接口、状态、日志与恢复入口。对应的工程入口见 [Harness](../engineering/HARNESS.md)。
