# SQL Server 数据库设计

## 数据职责

| 数据组 | 代表实体 | 目的 |
| --- | --- | --- |
| 配置 | equipment、protocol_connections、points | 设备与点位权威定义 |
| 历史值 | runtime_data、runtime_100ms_data、setpoint_data | 按类别保存业务观测 |
| 状态 | equipment_status | 保存变化点，支撑状态区间查询 |
| 报警 | alarm_event_inbox、alarm_events | 分开原始接收与最终生命周期 |
| 规则与业务 | alarm_statistics_rules、maintenance_shifts | 统计解释和有效排除区间 |
| 运维与审计 | 网关配置状态、部署日志、接口与操作记录 | 保存可恢复状态和责任证据 |
| 维保 | 标准版本、计划、任务、命令、事件与照片元数据 | 业务流程、并发和历史快照 |

建议按数据责任划分表和约束。若增加中心实时值缓存，应先明确时效、上传频率和容量预算，不能从“需要实时页面”直接推出全量实时入库。

## 集合入库与幂等

非报警接口以一个批次构造表值参数（TVP），通过短事务集合写入；批内先去重，数据库唯一约束处理已存在记录和并发。单请求上限属于接口契约，超过上限应拒绝或由发送方分批，不能静默截断。

报警按稳定 `event_id` 去重。重复发送已经接收的事件仍可得到成功确认，接收接口不修改最终生命周期。后台处理把生命周期修改与入箱处理标记放在同一事务，失败一起回滚。

## 索引与查询

设备、点位和业务时间是常见筛选维度。故障查询需要设备与地址的稳定关联，以及覆盖开始时间和结束时间的合理索引。索引设计要兼顾写入成本；同键、职责重复的索引不因名称不同就都有保留价值。

业务时间、接收时间、处理时间各自保留语义。不能用数据库接收顺序直接替代设备事件顺序，也不能用趋势页的 ID 上界宣称获得了完整事务快照隔离。

## 迁移重入是行为兼容问题

已有库升级和新库建立由版本账本管理有顺序的迁移，业务种子显式选择。旧迁移重跑不得把包含阈值或保养排除的新查询函数覆盖成旧定义；冲突数据应显式失败，不能静默清理来使迁移通过。

在线判断采用中心接收到心跳的时间，同时保留设备上报时间。历史业务与报警去重凭据不自动删除，防止清理后把旧重传重新当成新事件。

回归不仅验证“执行两次没有报错”，还应验证不同顺序执行后业务结果不退化。具体案例见 [报警规则与迁移推演](../exec-plans/examples/alarm-rules-migration.md)。

## 事务边界

分类批改与其审计记录一起提交；维保命令与版本检查按领域事务处理；远程设备动作无法与中心数据库组成一个本地事务，需要持久化意图与状态核实。强行把三类问题抽象成同一个“保存成功”会丢失故障语义。
