## 项目名称与简介

**SCADA × Harness Engineering｜AI 辅助开发参考方案**

以 SCADA 与设备管理为问题场景，编写覆盖需求、架构、数据、前后端、验证和交付的文档方案，提出通过仓库知识库、代理入口、工程约束与反馈闭环组织 AI 开发的方法。

## 可用于简历的要点

- **系统规划：** 设计边缘只读采集、SQLite 缓存补传、中心数据处理与 Vue 业务界面的职责边界，梳理实时数据、报警生命周期、报表统计和设备维保的协作关系。
- **Harness 应用：** 规划 AGENTS.md 路由、六类知识库、脚本调用允许集、分范围验证、CI 保守回退与上下文交接，明确人和 AI 在需求、实现与验收中的分工。
- **工程判断：** 通过报警区间归并、部署结果未知、维保并发与检查器漏检等问题推演，说明状态、幂等、事务、安全和验证之间的联系。
- **交付方法：** 提供阶段实施路线、验收矩阵、任务卡和交接模板，给出技术选型的适用条件、代价与重审时机。

**参考技术栈：** C# / .NET、ASP.NET Core、SQL Server、SQLite、Vue 3、Vite、ECharts、PowerShell、GitHub Actions。

## 一分钟讲述示例

> 我用 SCADA 和设备管理作为场景，规划了一套 AI 辅助开发方案。我关心的是如何把需求、数据一致性、前后端业务和交付验证连起来。比如采集数据要先落盘再上传，远程操作超时要先核实状态，维保审批要区分系统权限和业务责任。Harness 部分则给 AI 提供知识路由、执行边界和验证反馈，并通过交接维护当前上下文。每个重要选择都有适用条件、反例和验收思路。

## 技术追问与展开方向

| 问题 | 可以展开的内容 |
| --- | --- |
| 为什么不只写一个长 Prompt？ | 规则需要可定位，状态会变化，工具反馈能暴露部分偏离 |
| 如何判断 AI 方案是否合理？ | 业务不变量、替代方案、失败场景、可比较的验收标准 |
| 如何控制上下文成本？ | 最小导航、按任务读取、单一事实来源、交接替换 |
| 为什么检查器也要测试？ | 漏检和误报、语法变体、目录覆盖、Unicode 与失败回退 |
| 为什么优先简单架构？ | 当前约束、依赖成本、恢复复杂度，以及重新评估的证据 |
| 只有文档如何评价？ | 检查设计是否自洽、反例是否充分、实施和验证路径是否具体 |

## 展开一个问题的顺序

问题与约束 → 可选方案 → 我的建议与代价 → 状态或数据契约 → 反例 → 验证方法。可以选 [报警统计](../exec-plans/examples/alarm-rules-migration.md)、[网关恢复](../exec-plans/examples/gateway-recovery.md) 或 [维保流程](../exec-plans/examples/care-workflow.md)。
