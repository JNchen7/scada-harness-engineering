# 方案评审与验证清单

[作品集索引](index.md)

设计作品首先需要逻辑自洽，实施后还需要执行证据。这里给出评审这份方案的方法，以及将它落地时建议分阶段补充的验证。

## 文档层评审

| 维度 | 应回答的问题 |
| --- | --- |
| 目标 | 每个模块是否对应明确用户结果？不做事项是否清晰？ |
| 一致性 | 产品规则、数据模型、接口和页面是否采用同一语义？ |
| 状态 | 成功、失败、处理中、结果未知是否能区分？ |
| 取舍 | 建议有何适用条件、代价和替代方案？ |
| 可执行性 | 任务能否拆解？每步的输入、产物和验收是否明确？ |
| 可维护性 | 知识能否发现？规则和当前状态是否分别维护？ |

## 落地后的验证层级

| 阶段 | 建议准备的验证 | 结论范围 |
| --- | --- | --- |
| 静态检查 | 索引、链接、语法、允许集、边界规则 | 文档和受检结构 |
| 单元与性质验证 | 区间算法、状态机、重试、版本与权限反例 | 所覆盖的逻辑和输入 |
| 隔离集成 | 数据库事务、缓存恢复、API 幂等、进程退出 | 指定环境的组件协作 |
| 浏览器验收 | 查询、编辑、失败恢复、权限、布局与键盘路径 | 实际检查的页面与状态 |
| 环境试运行 | 设备只读、网络、磁盘、系统服务、手机摄像头 | 当次环境、版本和授权范围 |

每份结果记录对象、版本、输入、环境、时间、期望、实际、结论和未覆盖项。只有真正执行过的检查才填写结果；参考 [验证记录模板](../../templates/verification-report.md)。

## 四组高价值反例

1. 上传已被接收但响应丢失：边缘保留批次并以原身份重试，中心不产生重复业务。
2. 部署命令超时：先读取服务路径、任务阶段和新心跳，不能默认失败后重放。
3. 两人领取同一任务：只能有一个有效领取人，另一方得到可解释的冲突。
4. Git 差异只返回部分路径：丢弃不可靠清单，选择完整验证范围。

## 如何评价 AI 协作效果

选取复杂度可比较的任务，记录需求澄清、首次可用结果、返工、验证和交接耗时；按原因区分需求变化、上下文缺失、实现错误和验证遗漏。先建立基线，再观察哪些机制有帮助。

可跟踪任务完成质量、规则违规、重复错误、定位时间和交接成本。提交数量、文档数量或生成代码占比不能单独代表效率；没有测量就不填写提升比例。

## 本仓库的交付检查

维护时核对 Markdown 文件类型、分类导航、相对链接、锚点、术语、图表和差异格式。本文档仓库不提供应用运行环境；上面的运行检查是实施建议，不能仅由阅读文档判定通过。
