# 关键选择与设计计划

[产品规格索引](index.md)

下表给出我建议的关键选择，以及问题、代价和重审条件。选择应来自约束分析，而不是 AI 对某种技术的偏好。

| 建议选择 | 解决的问题 | 代价与重审条件 |
| --- | --- | --- |
| 边缘采集与中心业务分离 | 中心不直接承担 PLC 访问，断网仍可本地缓存 | 增加缓存与补传状态；需要单独验证恢复 |
| 模块化中心与显式 SQL | 让入库、事务和查询口径可检查 | 复杂查询需专门回归；不自动拥有 ORM 的抽象能力 |
| 按数据类型拆分缓存与接口 | 区分值、状态、报警的确认与幂等语义 | 需要维护跨层字段契约和各队列积压 |
| 报警入箱与生命周期分离 | 接收事务保持短，后台可恢复处理 | 要监控“已接收但未处理”的延迟 |
| 故障实例查询时归并 | 分类与阈值改变后即时采用新规则 | 查询成本需验证，不预先宣称适合任意规模 |
| 网关独立版本目录与服务路径切换 | 减少搬动活动文件导致的中间状态 | 需要持久化意图、读回状态与恢复判定 |
| 轻量前端与现有原生能力 | 让功能和状态可控，减少依赖 | 共享查询与交互规则仍要主动维护 |

## 分阶段规划

建议第一阶段跑通只读采集、历史和报警，按接入边界配置必要的身份保护。账号管理、版本恢复和维保可以按业务需求逐步深化；涉及手机、组织授权、标准快照和照片时，应同步扩展验收范围。

遇到新需求时，先识别改变的是哪个契约。例如增加维保照片并不意味着要改变 PLC 点表；停产保养对报表的排除规则也不等同于维保任务的完成状态。

## AI 协作中的决策责任

把已定业务口径、选项与约束写进知识库，AI 才能在限定空间内完成查证和实施。技术细节可自主推进；需要新业务定义、破坏性动作或新外部影响时再明确决定。

决策记录需要说明实际收益、代价、验证与重审条件。不能用“更先进”替代对当前问题的解释，也不能在每次重构中自动引入新的服务、队列或框架。

复杂决策的讨论见 [问题推演](../exec-plans/examples/index.md)。
