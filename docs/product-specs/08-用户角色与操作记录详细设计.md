# 用户角色与操作边界

[产品规格索引](index.md) · [认证实现契约](../design-docs/16-Web登录与权限设计.md)

建议将业务角色分为执行人员与审核人员。系统管理权限、业务签名资格和组织范围是不同维度。

## 权限模型

| 维度 | 回答的问题 | 典型约束 |
| --- | --- | --- |
| 系统管理员 | 谁能管理账号和系统功能？ | 不因此绕过 PLC 边界或维保禁止自审 |
| 页面查看权限 | 用户能看到什么功能？ | 明细、导出和汇总分别核对授权 |
| 操作权限 | 可以执行哪些变更？ | 操作权限依赖相应查看权限 |
| 业务级别 | 谁执行，谁确认？ | 执行人员不能确认自己参与的记录 |
| 组织归属 | 能处理哪些设备业务？ | 按完整组织路径，避免同名段落跨线授权 |

采集报表与维保可能需要不同的组织范围。建议逐个业务入口定义授权矩阵，不从一个模块的组织隔离推断全系统使用同一种行级权限。

## 谁决定什么

业务负责人确定统计口径和责任规则；维护者把它们落实为需求、设计与验收；AI 辅助完成相关实现、回归和检查。授权必须落在实际动作上，不能从“有管理页面权限”推出任意远程操作权。

## 操作记录的业务要求

关键配置修改应保存操作人快照、对象、实际原值和新值、时间与结果。用户改名或删除不能改写历史责任。后台任务在排队时捕获操作者，不能等待执行时从另一请求推断身份。

配置提交意图不等于设备实际生效，远程动作结果未知时必须保留未知或待核实状态。具体事务与记录策略见 [Web 操作记录](../design-docs/18-Web操作记录设计.md)。

## 典型验收

管理员仍不能自审；有页面权限但无变更权限的请求被服务器拒绝；组织权限撤销后，列表、详情、照片、导出和写操作一致收回；切换用户不复用前一账号的迟到响应和本机草稿。
