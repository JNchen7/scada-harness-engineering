# 最小编码范围与后续扩展

[产品规格索引](index.md)

建议用最小范围约束第一轮实施，先得到一个可验证的端到端闭环，再评估扩展。以下是一种实施顺序，不是已经完成的阶段记录。

## 第一阶段建议闭环

配置设备和点位 → 只读采集 → 边缘当前值与持久化 → 中心接收 → 报警生命周期 → 查询与报表。

| 第一阶段能力 | 最小成立条件 |
| --- | --- |
| 资产与点表 | 标识、类型、周期、地址和启用语义明确 |
| 值与状态入库 | 首次值、变化值和约定快照能保存，重传幂等 |
| 报警 | 开始、恢复、不重复、可追溯，不扩展派工与通知 |
| 缓存补传 | 先本地落盘，确认后删，失败保留 |
| Web | 能查设备、报警、趋势和基本统计，错误可解释 |
| 运维可见性 | 心跳、采集状态、缓存和接收积压有入口 |

## 可选扩展阶段

第二阶段可深化版本管理、账号权限、操作审计与报表交互；第三阶段可按需求增加设备维保、手机拍摄和组织隔离。基础身份保护应与访问范围匹配，不应因阶段划分而推迟必要的安全措施。每一阶段先确定业务收益，再扩展数据、页面及验收。

## 如何定义验收

验收要连接业务目标与异常行为：值能保存之外，还要看确认丢失是否误删缓存；报警能显示之外，还要看重复、孤立恢复和跨边界统计；表单能提交之外，还要看并发、权限与请求重试。

每个阶段分别定义完成实现、本机验证、隔离服务验证和环境验收的标准，并记录实际结果。

## 明确不扩展的方向

PLC 写入控制、通用协议市场、多租户平台、外部业务系统集成、完整组态、大规模预计算平台不因当前文档存在而成为项目能力。发生真实新需求时，应重新确定范围和证据要求。

## 对 AI 开发的作用

最小范围让代理知道哪些问题必须做完整、哪些扩展当前无需做。范围按用户结果划定，不按单个文件划定；新增表、状态或接口应同步检查相关契约，而不是只让代码编译通过。
