# 需求分析

[产品规格索引](index.md)

以设备监测与管理为假设场景，我建议先定义用户结果和业务边界，再决定模块及实施顺序。

## 用户问题与产品目标

设备数据分散在现场控制器和操作界面，管理与维护人员缺少统一查看入口。建议先建立采集、存储、查询与报警链路，再扩展网关维护、账号权限和设备维保。系统不承担安全联锁或 PLC 控制职责。

| 用户场景 | 需要的结果 | 能观察的验收 |
| --- | --- | --- |
| 查看设备当前情况 | 能区分最新观测、旧值、离线和采集异常 | 数值有采集时间，通讯状态独立展示 |
| 查找异常原因 | 能查询报警的开始、恢复、描述与发生模式 | 重传不制造重复生命周期，缺测不伪造恢复 |
| 分析故障 | 报表与明细使用同一统计口径 | 嵌套、重叠、跨边界区间可解释 |
| 维护采集实例 | 配置有版本，动作有状态，失败可核实 | 不能以启动命令成功代替采集成功 |
| 执行巡检与保养 | 有标准、任务、责任人与确认闭环 | 历史标准不被新标准改写，自审被阻止 |

## 数据范围

状态、报警、参数、设定值和诊断信息各有不同的采集与保存语义。少量高频点单独调度和预算，不能由个别高频需求推出全量高频上传。实时快照优先在边缘查看，中心承担历史、事件与业务数据。

资产采用工厂、线别、阶段、工序、设备的层级。公开示例只使用“示例工厂 / 产线 A / 阶段 A / 工序 A / DEMO-001”。层级名称表达业务归属，不代表真实组织。

## 关键约束

- PLC 访问保持只读，不能用探索、写点或控制测试代替已定义的读取契约。
- 网络中断时保留有效待上传数据；磁盘不足必须暴露保护状态，不能承诺无限缓存。
- 业务查询与权限在服务器端成立，前端隐藏按钮不能单独构成安全控制。
- 需求、实现和验收分开：资料中列出的愿景不自动等于已实现能力。

## 当前不作出的承诺

本方案的范围是设备监测、数据与维保管理，不扩展为完整组态、MES 或工业安全系统。报警推导的故障时长需要业务解释，不能直接等同于工艺确认的停产时间。
